\section{Conclusion}\label{section:conclusion}

% Summarize what we did? Bit like the introduction but a little more detail on exactly what we did, so the reader remembers.

In short we have made an implimentation of the Rizzo language by \citeauthor*{rizzo_modal_2025}~\cite{rizzo_modal_2025}, with a reference counting memory management system based on \cite{ullrich_counting_2021}, and a transpiler to C. In C we have implemented the step, update and advance semantics of Rizzo, which we have tested and evaluated on a number of examples compiled from RizzoLang to C.

% Evaluation - what did we figure out

During our evaluations we identified both sucesses and limitations of our implementation and the Rizzo language in general. We found that unused signals, like intermediate signals in the signal constructor, is imidiately deallocated by the reference counting instructions. This solves the issue we set out to fix in this paper, as it ensures we dont update dead signals during the step semantics. 
In our evaluation of the memory we were not able to find any signs of memory leaks or space leaks. Which makes us confident in our reference counting implimentation. 

% Which shows we live up to the expectations of memory safety that \cite{rizzo_modal_2025} was trying to achieve with the mutable signals.  

For the reuse of memory we have identified a quirk in the semantics of Rizzo, and an issue caused by a limitation in our implimentation.

The quirk in the semantics is causing signals passed to signal combinators, to be unable for reuse, like we can with lists and other constructors.
For example, the signal combinator, $map \; f \; s$, will result in a new signal $s'$, which will have a dependency on a future value of $s$. This makes it impossible to reuse the signal $s$ for $s'$, as we would lose the future value of $s$ that $s'$ is depending on if we did.
The issue in the implimentation is with intermediate signals. These signals are created as part of the update semantics, but are often only created to store the updated valuees, before copying them back to the signal that was updated. This is often wasteful and should be avoidable, but the compiler does not have enough knowledge about the usage of the object in the advance semantics.
To prevent this issue, we have proposed a possible solution. The solution gives the compiler more information, which should allow the compiler to better reuse the intermediate signals.
